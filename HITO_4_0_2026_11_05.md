# Hito 4.0 — Publicación estable y recuperación

Implementado el 5 de noviembre de 2026. Alcance: flujo de actividades del cliente y servidor activos; sin migraciones, escrituras en Supabase ni enriquecimiento masivo.

## Comportamiento

- La generación de preguntas ya no transmite borradores del enunciado. Se completa el contenido, se comprueba el contrato y se realiza la revisión antes de enviarlo como resultado final. Reparación y selección de reserva ocurren antes de mostrar una pregunta.
- El canal de actividades transmite únicamente estados de preparación antes del resultado final. Existe una protección adicional en el router y otra en el cliente: incluso un proveedor de contenido antiguo o simulado que intente emitir borradores no los muestra al estudiante.
- Se conserva la preparación anticipada después de guardar la respuesta. La primera actividad en frío puede implicar más espera visible que antes: ya no se utiliza la aparición de texto sin aprobar como sustituto de una actividad lista.
- La reserva se limita al mismo paso objetivo y habilidad declarada. Se verifica su contrato y presentación antes de seleccionarla. Si no existe una reserva compatible, se ofrece reintento o salida, sin sustituir el objetivo ni inventar un intento. Los metadatos heredados aún requieren auditoría; esta compatibilidad técnica no certifica veracidad o adecuación pedagógica.
- Un fallo de evaluación o guardado conserva la pregunta y el texto o las selecciones. Una caducidad tampoco borra lo escrito: se conserva para copiarlo antes de elegir explícitamente otra actividad.
- El borrador se guarda en `sessionStorage` por usuario y módulo. Al retomar, el servidor verifica el token cifrado, su propietario, caducidad, módulo y paso. Si la respuesta ya quedó registrada pero se perdió la confirmación, recupera el feedback y la respuesta realmente evaluada sin generar otro intento.
- La recuperación funciona con una instancia nueva de servidor mientras el token siga vigente y se conserve el secreto de firma. No requiere reescribir contenidos históricos.
- El cambio de sesión retira la pregunta y las respuestas visibles e invalida solicitudes anteriores. Las respuestas tardías de solicitudes anteriores no deben sobrescribir el estado del recorrido actual.
- Los detalles por alternativa y el resumen de práctica conservan su presentación. El aviso técnico de reserva se mantiene durante pruebas, como se acordó anteriormente. Las ayudas siguen utilizando su flujo progresivo propio; el cambio de publicación de este bloque se aplica a las actividades.

## Fallos y medición

Se registran categorías limitadas: conexión, límite de proveedor, autenticación del proveedor, indisponibilidad, tiempo agotado, salida incompleta, negativa, contrato inválido, rechazo pedagógico y pregunta repetida. Los mensajes libres del proveedor no se incorporan a las métricas.

Se conserva como máximo una reparación automática dentro del presupuesto compartido de generación de 22 segundos. Los fallos de disponibilidad o una negativa no se resuelven con reintentos ilimitados. La recuperación de un intento guardado no vuelve a evaluarlo.

Las métricas distinguen:

- Generación en frío, entrega de una actividad preparada y relectura de una ya publicada.
- Resultado de construcción: generado, calculado, reserva o no disponible.
- Primer fallo, reparación y fallo final.
- Recuperación pendiente o ya respondida.
- Error terminal del canal aunque su cabecera HTTP ya fuera 200.

Una actividad preparada solo cuenta como tal en su primera entrega; los reintentos posteriores se clasifican como relecturas. Las construcciones incluyen preparación en segundo plano, para no ocultar su consumo.

Para registrar mediciones reales, opcionalmente iniciar desde `server/` con:

```powershell
$env:KUNEO_METRICS_FILE = 'logs/learning-runtime.jsonl'
npm run dev
```

Después, desde la raíz del proyecto:

```powershell
node scripts/quality/hito4-metrics.cjs server/logs/learning-runtime.jsonl
```

El informe calcula p50/p95 separados para las tres clases de entrega. Los tiempos de servidor no incluyen red del cliente ni renderizado. Una muestra pequeña no establece un objetivo de producción. No se obtuvieron nuevas mediciones con OpenAI/Supabase reales en esta entrega; no se atribuye una mejora de latencia al cambio de presentación.

## Verificaciones ejecutadas

- **76 pruebas automatizadas aprobadas**, incluyendo propiedad, caducidad, recuperación tras reiniciar servidor, confirmación de inserción perdida, ausencia de intentos duplicados, fallos antes/durante generación, reparación, revisión, evaluación y persistencia.
- Interrupción de conexión durante generación y petición concurrente: una sola construcción y una misma identidad final.
- Rechazo de revisión y reparación: ningún texto descartado llega al canal de actividades; la respuesta final queda estable en caché.
- Selección de reserva: no se permite cambiar a otro paso o habilidad para ocultar la ausencia de material compatible.
- Métricas: distinción entre primera entrega preparada y relectura, y reconocimiento de un error terminal en un canal HTTP 200.
- **Ocho comprobaciones aprobadas en navegador** con el componente real `LearningModule` y servicios simulados: abierta, selección única, selección múltiple y parejas conservan respuesta al fallar, retomar y reintentar; confirmación perdida recuperada sin otro envío; caducidad conserva el texto; cierre/cambio de sesión retira datos visibles; ningún borrador no aprobado aparece en el DOM.
- ESLint de los archivos de cliente modificados y compilación de producción aprobados.
- No se utilizaron usuarios reales ni se insertaron intentos en Supabase para estas verificaciones. La interfaz de prueba usa un servidor temporal de loopback, detenido al finalizar; no se inició otro servidor en el puerto 3001.

Reproducir pruebas de servidor: `npm test` desde `server/`.

Reproducir la comprobación de navegador: `node scripts/quality/hito4-ui.cjs` desde la raíz, abrir la URL local que devuelve y pulsar «Ejecutar comprobaciones de interfaz». Usa datos simulados y no solicita credenciales.

## Límites y siguiente etapa

Los tests HTTP usan base de datos y proveedor simulados; la prueba de navegador también simula sus servicios. No constituyen una prueba completa con la infraestructura real ni una certificación de exactitud del contenido.

La recuperación del borrador depende del almacenamiento de sesión del navegador y de un token vigente. No ofrece sincronización entre dispositivos ni almacenamiento offline completo. La idempotencia concurrente sigue utilizando una cola en memoria; antes de varias instancias se necesitará una garantía de unicidad en la base de datos.

Las reservas actuales siguen sin una certificación pedagógica individual. Al exigir compatibilidad habrá casos que ahora muestren un error recuperable donde antes se escogía otro objetivo. Esto debe cuantificarse en 4.1 y resolverse mediante auditoría y contenido aprobado en 4.2–4.4.

Para probar operativamente: reiniciar servidor y cliente, comenzar una práctica nueva, escribir o seleccionar una respuesta, comprobar reintento/recarga y confirmar que no se sustituye una actividad durante su presentación. No es necesario ejecutar SQL.

Siguiente entrega: diagnóstico de lectura de 4.1 y selección de las primeras cinco preguntas existentes a auditar. No iniciar generación por lotes antes de esa revisión.
